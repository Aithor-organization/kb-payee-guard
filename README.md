# KB Payee Guard — 계약서 기반 해외송금 무결성 게이트

> 해외송금 신청 시 **법으로 이미 제출되는 계약서**를 읽어, **계좌 변경 지시가 계약이 정한 절차를 따랐는지** 대조하고 어긋나면 송금을 **보류**하는 게이트.

**제8회 KB A.I Challenge** 출품 후보 · **금융 자유주제**

> 현직자 Pick #6 "수출입 금융 지원 에이전트"와 무대(수출입·무역금융·신용장)는 겹치나,
> Pick #6이 규정한 일은 *"환율·무역통계 분석 → 외환 리스크 관리, 무역금융 정보 제공,
> 환헤지 전략·외화 금융상품 추천"* 으로 **정보 제공·추천**이다.
> 본 과제는 **송금 차단 게이트**라 결이 다르므로 자유주제로 출품한다 (2026-07-31 공고 원문 대조).

## 문제

무역 대금을 지급하는 기업에게 *"거래 은행이 바뀌었으니 새 계좌로 보내주세요"* **메일 한 통**이 옵니다. 3년 거래한 담당자 이름으로 오고, 인보이스도 첨부돼 있습니다. 송금합니다.

3주 뒤 상대가 연락합니다. **"대금이 아직 안 들어왔는데요."**

도메인이 `@bauer-gmbh.de`가 아니라 `@bauer-gmbh.co`였습니다. **글자 하나.**

- 국내 접수 **약 1,600건** (2021~2025 상반기, 금감원)
- 손실은 **대금 전액**, 회수는 **사실상 0**
- **피해자는 "사기 판별 앱"을 켤 이유가 없습니다** — 속은 줄 모릅니다

### 🔴 그런데 더 어려운 케이스가 있습니다

위 사례는 **도메인이 위조**돼 있어서 메일 보안 제품이 잡을 수 있습니다. 하지만 **거래처 메일 계정 자체가 탈취되면 도메인이 진짜**입니다. 발신 주소도, 회신 스레드도, 문체도 전부 정상입니다.

그리고 사기범은 **굳이 다른 나라 계좌를 쓸 이유도, 결제방식을 바꿀 이유도 없습니다.** 같은 독일에 같은 법인명으로 계좌를 열면 됩니다.

> **이 경우 무엇이 남는가?** — 계좌번호가 바뀌었다는 사실, 그리고 **그 지시가 계약서가 정한 경로로 오지 않았다는 사실**입니다.

## 🔴 이건 새로운 아이디어가 아닙니다

이 문제를 다루는 제품과 제도가 이미 여럿 있습니다. [조사노트 §E-3](docs/00_조사노트.md)에 전부 기재했습니다.

| 이미 있는 것 | 무엇을 검증 | 위 "더 어려운 케이스"에서 |
|---|---|---|
| Proofpoint · Trend Micro | 메일 도메인·문체 | ❌ **도메인이 진짜라 통과.** 애초에 송금을 못 막는다 |
| Trustpair · Eftsure · Trustmi | **벤더 마스터** 계좌 이력 | ⚠️ 계좌 변경은 감지하나 **정당/사기를 못 가른다.** ERP 전용(대기업) |
| iPiD · **EU VoP** (2025-10 법정) | **이름 ↔ 계좌** | ❌ **법인명으로 계좌를 열면 통과.** EU 역내 유로만 |
| **하나·우리은행** 수취계좌 사전확인 | 이름·계좌·BIC | ❌ 동일 + **영업점 방문 + 사용자 능동 요청** |
| 국내 **6개 은행 업무 매뉴얼** (2018~) | 계좌 변경 시 유선 확인 | ⚠️ 방향은 맞으나 **사람 판단.** 계약서 대조 없음 |
| 🎯 **우리** | **계좌 지시가 계약 절차를 따랐는가** | ✅ **계약서 §Amendment는 위조 불가** |

**이름 대조 방식의 한계를 벤더 자신이 인정합니다:**

> *"사기범이 공급업체의 **정확한 법인명으로 계좌를 개설하면 이름 대조는 통과**한다."* — [Eftsure](https://www.eftsure.com/blog/products/top-6-bank-account-verification-software-in-2025/)
> *"VoP는 이름이 계좌와 일치하는지 확인하지만 **신분 도용은 탐지되지 않는다**."* — [Trustpair](https://trustpair.com/blog/verification-of-payee/)

> 🔴 **경쟁 제품 전부가 "계좌라는 값"을 검증합니다.** 값은 사기범이 통제할 수 있습니다. 저희는 **"그 값을 알려준 경로"** 를 검증합니다 — 경로 규칙은 계약 체결 시점에 잠겨 있습니다.

## 🎯 그런데 비어 있는 구간이 있습니다

**금감원이 전 은행에 지시했습니다:**

> *"**수취인 국가와 수취 은행 소재 국가가 서로 다르거나** 계좌번호가 평소와 다른 경우 **다시 확인하는 절차**를 거치도록"* — [KBS](https://news.kbs.co.kr/news/pc/view/view.do?ncd=8547381)

**그리고 은행은 이미 계약서를 받고 있습니다** — 외국환거래법상 연 10만 달러 초과 송금은 계약서 제출 의무.

> **은행은 계약서를 받아 "정당한 거래 목적인가"(자금세탁 방지)를 확인합니다.
> 그런데 그 계약서가 정한 상대방·결제조건·계좌 변경 절차와 실제 송금이 일치하는지는 확인하지 않습니다.**

**이것이 우리 자리입니다.** 서류는 이미 옵니다. 아무도 읽지 않을 뿐입니다.

## 🎯 핵심 신호 — 계약서 한 장으로 나옵니다

| ID | 신호 | 신규성 |
|---|---|---|
| 🎯🎯 **S16** | **계좌 지시 출처** ≠ 계약이 정한 절차 (§Notices·§Amendment) | **최빈 BEC를 잡는 유일한 축** |
| 🎯 **S9** | 계약 당사자 **소재국** ≠ 수취계좌 개설국 | **금감원 지시 항목** |
| 🎯 **S10** | 계약서 **결제조건** ≠ 실제 송금방식 | **기존 제품 사용 확인 0건** |
| S11 | 계약서 수익자명 ≠ 수취인명 | VoP와 중복 |
| S1 | 신규 수취계좌 | **트리거일 뿐 판별자 아님** — 정상 변경도 이력이 없다 |

### S16이 왜 결정적인가

**가장 흔한 BEC는 국가도 이름도 결제조건도 전부 그대로**입니다. **계좌번호만** 바뀝니다.
그 케이스에서 S9·S10·S11은 전부 침묵합니다. 남는 질문은 하나입니다:

> **"이 계좌 지시가 계약이 정한 경로로 왔는가?"**

계약서 §Notices·§Amendment는 **체결 시점에 확정되어 사기범이 사후에 바꿀 수 없습니다.**
메일 주소는 위조해도, 3년 전 계약서의 *"변경은 양측 서면 합의로"* 는 위조할 수 없습니다.

그리고 **은행은 송금 신청 시 "이 계좌 정보를 어디서 받으셨습니까"를 이미 묻습니다** — 사용자 능동성 0.

### S10이 왜 강력한가

계약서가 **L/C**인데 **T/T**로 보내라고 하면 사기의 전형입니다. L/C는 은행이 지급을 보증하므로 사기범이 가져갈 수 없고, **T/T는 계좌로 직접 들어갑니다.** 사기범에게 결제 방식을 바꿀 **구조적 동기**가 있습니다.

> ⚠️ **방향을 구분합니다.** T/T → L/C(더 안전한 방향)는 경고하지 않습니다. 무조건 경고하면 게이트가 꺼집니다.
> 🔴 **단 정상 거래에서 L/C→T/T가 얼마나 흔한지는 측정하지 않았습니다** (R-8).

## 핵심 설계 원칙

| 원칙 | 내용 |
|---|---|
| **켜지 않아도 작동** | 별도 앱이 아니라 **송금 신청 흐름 안**에 있습니다 |
| **판정이 아니라 대조** | 확률을 말하지 않습니다. *"계약서에 뭐라 적혔고 이번 송금은 어떻다"* 만 말합니다 |
| **추가 서류 요구 0** | 법정 제출 서류만 씁니다 |
| **LLM은 판정하지 않음** | 등급은 규칙 테이블이 정합니다 — 프롬프트 인젝션 방어 |
| 🎯 **계약 체결 시점을 신뢰 기준으로** | §Notices·§Amendment·기재 연락처 — 전부 계약 시점에 확정 → **사기범이 사후에 바꿀 수 없습니다** |
| **모든 규칙은 발화해야 한다** | 입력이 없는 규칙은 배포 금지 — 도달성 전수 검사(T15). *조용한 침묵은 오탐보다 위험합니다* |

## 🎯 판정에 튜닝할 계수가 없습니다

```
❌ "이 변경은 사기 확률 87%"                → 정답 라벨 필요. 가중치 튜닝 필요
✅ "계약서 §14는 서면 합의를 요구하는데 이번 지시는 이메일"  → 두 문서에서 직접 나오는 사실
```

규칙의 **조건이 곧 사용자에게 보이는 문장**입니다. 조정할 가중치도 임계값도 없습니다.
대신 **공격 테스트 16종**으로 *"이 조합은 대조로 걸린다"* 를 증명합니다.

> 🔴 **단 "평가가 필요 없다"는 뜻은 아닙니다.** 판정이 결정론이어도 **입력(계약서 추출)이 틀리면 결과는 확정적으로 틀립니다.** 계약서 §Notices·§Amendment 추출 정확도가 **시스템 정확도의 상한**입니다.

🔴 **"실제 사기를 N% 잡는다"고 주장하지 않습니다.** 자체 설계 시나리오에 대한 수치는
[아래](#-게이트가-실제로-무엇을-막고-무엇을-통과시키나)에 있으나, 실제 BEC 사건 데이터가 아닙니다.

## 구현 기반

**AITHOR-Agent-Framework** 위에 도메인 로직만 얹습니다.

- 승인 게이트가 **코드로 강제** — *"모델이 `approval_id`를 스스로 만들어 넘는 것도 차단"*
- `aithor_agent_framework.guard.RuntimeGuard` 3중 검문 (입력·**도구결과**·출력)
  ⚠️ 워크플로우 스키마의 `adapter: AgentShield.RuntimeGuard` 는 어댑터 **이름**이고,
  실체는 프레임워크 내장 guard 다 (AgentShield 에서 영감을 받은 별도 구현)
- 워크플로우 스키마의 `kind: deterministic`이 **"LLM은 판정하지 않는다"를 강제**
- 프레임워크 테스트 **1,264 통과 / 22 skip · 34.6초** (2026-08-02 macOS 실측, API 키 불필요)
  샌드박스 OS 격리 3건은 macOS 에서 실패 — Linux 전용 `RLIMIT_AS`·네임스페이스 의존 [추정]
- 코어 stdlib only, 의존성 0

### 🎯 AI가 없으면 이 제품이 성립하지 않는다 — 수치

S16은 `[계약이 허용한 경로] ∩ [이번 지시가 온 경로]`를 계산한다. 오른쪽은 은행이 폼으로 묻지만,
왼쪽은 **계약서 자연어에만** 있다. 그 추출 정확도가 곧 시스템 정확도의 상한이다.

| 추출기 | 정확도 | Recall |
|---|--:|--:|
| 정규식 | 30.0% | **20.8%** |
| **LLM** | **90.0%** | **91.7%** |

실물 계약서 30건 전수 · [`docs/05_베이스라인A_실측.md`](docs/05_베이스라인A_실측.md)
정규식은 **해석에서 지기 전에 조항을 찾지 못한다**(오답 21건 중 19건이 미탐지).

### 🎯 게이트가 실제로 무엇을 막고 무엇을 통과시키나

| 추출 경로 | BEC 탐지율 (알려진 사각지대 제외) | 정상거래 오탐률 |

정규식으로 추출하면 **공격의 83%가 통과한다** — 게이트가 사실상 꺼진다.

🔴 **알려진 사각지대**: 사기범이 **수정 합의서를 위조**하면 통과한다(30건 전건 미탐).
S16은 지시의 *경로*를 보지 문서의 *진위*를 보지 않는다. 통과할 것을 알면서 평가셋에 넣었다 —
숫자를 좋게 만들려고 빼면 심사에서 물었을 때 답이 없다.

⚠️ 이 숫자는 **자체 설계 시나리오** 기준이고 오탐 발견 후 규칙을 고쳤다. 실제 사기 탐지
성능이 아니라 *"설계 의도대로 동작하는가"* 의 검사다 ([`06` §5](docs/06_E2E_탐지율_오탐률.md)).

## 로드맵

```
P1 워크플로우 + HITL 게이트 + 승인 원장          ← 여기부터
P2 L1 계약서 판독 (§Notices·§Amendment 포함) + UNKNOWN 경로
P3 L2 대조 (S16·S9·S10·S11·S12)                 ← 가치 정점
P4 L3 보조 신호 (M1·M2·M6·M8 + S1 트리거)
P5 L4 규칙 11개(R10 제외) + L5 근거 생성 + 도달성 검사
P6 송금 신청 화면 시뮬레이터
P7 감사 + 컴플라이언스 팩
```

**막는 것을 먼저 만들고, 판단하는 것을 나중에 붙입니다.** 안전 불변식 없이 판정 로직을 쌓으면 나중에 우회 경로가 남습니다.

> **P2가 P3의 상한을 정합니다.** §Notices·§Amendment를 못 읽으면 S16이 전부 중위험으로 떨어져 모든 건이 `HOLD` — 게이트가 꺼집니다.
