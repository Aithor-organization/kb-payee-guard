# KB Payee Guard

**해외송금 신청 시 이미 제출된 계약서를 AI가 읽어, 이번 계좌 지시가 계약이 정한 변경 절차를 따랐는지 대조하고 어긋나면 송금을 보류하는 게이트.**

제8회 KB A.I Challenge · 금융 자유주제 · 팀 aithor

```
python3.12 -m unittest discover -s tests     # 설치 없이 바로 실행됩니다 (128건, 1초 미만)
```

## 30초 요약

무역 대금을 보내는 기업에 *"거래 은행이 바뀌었으니 새 계좌로 보내주세요"* 메일이 옵니다.
3년 거래한 담당자 이름, 인보이스 첨부. 송금합니다. 3주 뒤 상대가 말합니다 — **"대금이 안 들어왔는데요."**

국내 **무역송금 사기 접수** 약 1,600건 (2021~2025 상반기, 금감원 집계 · [KBS 보도](https://news.kbs.co.kr/news/pc/view/view.do?ncd=8547381)).
건당 손실이 **대금 전액**에 이를 수 있고, 해외 계좌로 나간 자금이라 **회수가 어렵습니다**
(사건별 손실·회수 분포 통계는 확보하지 못했습니다).

이 사기를 막는 제품은 이미 여럿 있습니다. 계좌 변경 자체를 판정하는 제품들은
**"이 계좌번호가 이 회사 것이 맞나"** 를 확인합니다(메일 보안 제품은 축이 다릅니다 — 아래 표).
그래서 사기범이 **거래처와 같은 법인명으로 계좌를 개설하면 통과**합니다 —
유사 상호 법인 설립이나 계정 탈취 후 명의 도용으로 실제 일어나는 일이고, **벤더 자신이 인정합니다**(아래 인용).

**KB Payee Guard는 계좌번호를 검증하지 않습니다. 그 계좌번호를 알려준 경로를 검증합니다.**

> 계좌번호는 바꿀 수 있어도, **은행이 이미 보관 중인** 3년 전 계약서의
> *"변경은 양측 서면 합의로"* 는 사후에 바꿀 수 없습니다.
> (새 수정합의서를 위조하는 공격은 별개입니다 — 아래 성능표에서 전건 미탐입니다.)

## 한 장으로 보는 동작

```
 제출된 계약서 (2023-04-11)              이번 송금 신청
   상대방    BAUER GmbH                    수취계좌   LT12 … 47   🇱🇹
   소재지    Stuttgart, Germany 🇩🇪         송금방식   T/T
   결제조건  Irrevocable L/C                계좌 지시  이메일 한 통
   §14 변경  "서면 합의로만"
                    │                            │
                    └───────────  대조  ──────────┘
                                   ↓
   ▸ 계약서 §14는 계좌 변경을 서면 합의로 제한합니다.          ← S16 (판정 축)
     이번 지시는 이메일 한 통입니다.
   ▸ 계약 상대방은 독일인데 계좌 개설국이 리투아니아입니다.     ← S9  (금감원 지시 항목)
   ▸ 계약서는 L/C 결제인데 이번엔 T/T입니다.                   ← S10
     L/C는 은행이 지급을 보증하지만 T/T는 계좌로 바로 들어갑니다.
                                   ↓
                        송금 보류 · 사람 승인 요구
```

**은행 송금 신청 흐름에 내장하는 것을 목표로 하는 코어**입니다 — 그러면 사용자가 앱을 켤
필요가 없고, 속은 줄 모르는 피해자도 반드시 거칩니다. (현재는 CLI·라이브러리 코어 +
**로컬 데모 화면**까지. **은행 시스템 연동·외부 REST API는 미구현** — 로드맵 P7.)

**계약서가 이미 확보된 거래라면 추가 서류를 요구하지 않습니다** — 외국환거래규정상
**연 10만 달러 초과 송금**은 지급 사유 **입증서류** 제출 의무가 있고, 무역대금에서는 통상
계약서가 그 서류입니다. 다만 **계약서가 항상 필수인 것은 아니므로**, 이 게이트의 대상은
**계약서가 증빙으로 제출된 거래**로 한정됩니다.
→ 즉 이 게이트의 **1차 적용 범위는 계약서가 제출되는 고액 무역송금**입니다. 그 아래 구간은 대상이 아닙니다.

> 은행은 그 계약서로 *"정당한 거래 목적인가"*(자금세탁 방지)를 확인합니다.
> 그런데 **그 계약서가 정한 계좌 변경 절차와 이번 송금이 일치하는지를 대조한다는 자료는
> 공개 범위에서 찾지 못했습니다** (은행 내부 프로세스 미확보 — 단정이 아니라 미확인입니다).
> 서류는 이미 옵니다. 그 서류의 이 항목이 쓰이고 있다는 근거를 못 찾았을 뿐입니다.

## 실제로 돌린 결과

위 다이어그램과 같은 케이스를 판정 엔진에 그대로 넣은 **실행 출력**입니다.
아래 코드를 복사해 붙이면 같은 결과가 나옵니다 (API 키 불필요).

<details>
<summary>입력 (계약서 사실 + 송금 신청) — 클릭</summary>

```python
facts = ContractFacts(
    counterparty_name="BAUER GmbH", counterparty_country="DE",
    registered_contact=["ap@bauer-gmbh.de"],
    payment_terms=PaymentTerms.LC, contract_date="2023-04-11",
    notice_channel_types=["POSTAL", "EMAIL"],
    amendment_clause="§14.2 Any change of bank account shall be effective "
                     "only upon written agreement of both parties.",
    amendment_clause_requires_written=True,
)
req = RemittanceRequest(
    case_id="DEMO-001", payee_name="BAUER GmbH",
    new_account=Account(number="LT121000011101001047", bic="REVOLT21"),   # 🇱🇹
    amount=Money(184500.0, "EUR"), remittance_type=PaymentTerms.TT,       # 계약은 L/C
    account_instruction=AccountInstruction(source=InstructionSource.EMAIL,
                                           channel_detail="ap@bauer-gmbh.co"),
    has_contract=True, change_request_sender="ap@bauer-gmbh.co",          # .de → .co
)
rules.evaluate(facts, req)
```

</details>

**사기 케이스 — 차단**

```
verdict : Verdict.BLOCK_PENDING   rule: R2

  - 계약서는 계좌 변경을 서면 합의로 제한하는데 이번 지시는 이메일입니다.
  - 계약 상대방 소재국은 DE인데 수취계좌 개설국은 LT입니다.
  - 계약서 결제조건은 L/C(화환신용장)인데 이번 송금은 T/T(전신송금)입니다.
    L/C는 은행이 지급을 보증하지만 T/T는 계좌로 바로 들어갑니다.
  - 발신 도메인 'bauer-gmbh.co'이 계약서 기재 도메인 'bauer-gmbh.de'과 유사하지만 다릅니다.
  - 계좌 변경 요청 메일이 기존 대화 스레드에 이어지지 않습니다.
```

**정상 계좌변경 — 통과** (같은 계약서, 수정 합의서로 온 독일 계좌 · L/C 유지)

```
verdict : Verdict.PASS            rule: R0
```

이 문장들은 **LLM이 쓴 것이 아닙니다.** 규칙 테이블이 조건을 그대로 문장으로 낸 것이라,
같은 사실이 들어오면 항상 같은 문장이 나옵니다. **문구 생성에 모델이 개입하지 않습니다.**
(다만 어떤 사실이 추출되느냐는 LLM이 정하므로, 어느 규칙·문장이 나올지에는 영향을 줍니다.)

> ⚠️ **현재 범위**: CLI·라이브러리 코어 + **로컬 데모 화면**(`scripts/demo_server.py` — 아래
> [1-bis단계](#1-bis단계--브라우저에서-사이트-열어-보기-키-불필요))까지입니다.
> 데모 화면은 `127.0.0.1` 로컬 전용이고 인증·영속이 없습니다 — **외부 REST API·은행 시스템
> 연동은 미구현이며 본선 구간**입니다 (로드맵 P7).

## 왜 기존 방식으로는 안 되는가

상용 제품 7종 · EU 법정 제도 · 국내 은행 2곳 · 6개 은행 업무 매뉴얼을 조사했습니다
([조사노트 §E-3](docs/00_조사노트.md)). **조사한 범위 안에서 공통점이 하나 있습니다 — 계좌 변경 자체를 판정하는 제품은
"계좌라는 값"(이름·번호·이력)을 검증합니다.** 값은 사기범이 통제할 수 있습니다.
(메일 보안 제품은 축이 달라 송금 자체를 막지 못하고, 은행 업무 매뉴얼의 유선 확인은
사람 판단이라 계약서 대조가 없습니다 — 아래 표 참조.)

| 이미 있는 것 | 무엇을 검증하나 | 계정 탈취 + 같은 나라·같은 법인명이면 |
|---|---|---|
| Proofpoint · Trend Micro | 메일 도메인·문체 | ❌ 도메인이 진짜라 통과. 애초에 송금을 못 막음 |
| Trustpair · Eftsure · Trustmi | 벤더 마스터 계좌 이력 | ⚠️ 변경은 감지하나 **정당/사기를 못 가름**. ERP 전용(대기업) |
| iPiD · **EU VoP** (2025-10 법정) | 이름 ↔ 계좌 | ❌ **법인명으로 계좌를 열면 통과.** EU 역내 유로만 |
| 하나·우리은행 수취계좌 사전확인 | 이름·계좌·BIC | ❌ 동일 + 영업점 방문 + 사용자 능동 요청 |
| 국내 6개 은행 업무 매뉴얼 (2018~) | 계좌 변경 시 유선 확인 | ⚠️ 방향은 맞으나 **사람 판단**, 계약서 대조 없음 |
| **KB Payee Guard** | **계좌 지시가 계약 절차를 따랐는가** | ✅ **은행 보관 원본 기준이면 사후 변경이 어려움**\* |

한계를 벤더 자신이 인정합니다:

> *"사기범이 공급업체의 **정확한 법인명으로 계좌를 개설하면 이름 대조는 통과**한다."*
> — [Eftsure](https://www.eftsure.com/blog/products/top-6-bank-account-verification-software-in-2025/)
>
> *"VoP는 이름이 계좌와 일치하는지 확인하지만 **신분 도용은 탐지되지 않는다**."*
> — [Trustpair](https://trustpair.com/blog/verification-of-payee/)

그리고 **금감원이 전 은행에 지시한 항목**이 우리 신호와 그대로 겹칩니다:

> *"**수취인 국가와 수취 은행 소재 국가가 서로 다르거나** 계좌번호가 평소와 다른 경우
> **다시 확인하는 절차**를 거치도록"* — [KBS](https://news.kbs.co.kr/news/pc/view/view.do?ncd=8547381)

## 판정 축 — S16

국가도 이름도 결제조건도 그대로이고 **계좌번호만** 바뀌는 유형이 있습니다
(사건별 분포는 공개 통계를 확보하지 못해 "가장 흔하다"고 단정하지 않습니다).
이 케이스에서 **우리가 구현한 다른 신호는 전부 침묵합니다.** 남는 질문은 하나뿐입니다:

> ### "이 계좌 지시가 계약이 정한 경로로 왔는가?"

계약서 §Notices·§Amendment는 **체결 시점에 확정되므로, 은행이 보관 중인 원본을 기준으로 삼는
한** 사기범이 사후에 바꿀 수 없습니다. 메일 주소는 위조해도 3년 전 조항은 그대로입니다.
🔴 **다만 새 수정합의서를 위조해 제출하는 경로는 막지 못합니다**(전건 미탐 — 아래 성능표).
\* 다만 **새로 제출되는 수정합의서를 위조**하면 뚫립니다 — 실측 전건 미탐(아래 성능표).
S16의 오른쪽 입력(=이번 지시가 온 경로)은 **송금 신청 폼의 항목 1개**로 받습니다.

> 🔴 **미확인**: 국내 은행이 이 항목을 **이미** 묻는지는 확인하지 못했습니다. 서식 실물을
> 확보하지 못했습니다. 묻지 않는다면 **드롭다운 1개를 추가**해야 합니다 — 새 서류가 아니라
> 기존 폼의 필드 하나이고, 사용자는 선택만 하면 됩니다. 다만 **"사용자 부담 0"이라고
> 단정할 수는 없습니다.** 확인 전까지는 "부담 최소"가 정확한 표현입니다.

| ID | 신호 | 신규성 |
|---|---|---|
| **S16** | **계좌 지시 출처 ≠ 계약이 정한 절차** (§Notices·§Amendment) | 동일국·동일명의 시나리오에서 **구현 신호 중 유일하게 발화** |
| S9 | 계약 당사자 소재국 ≠ 수취계좌 개설국 | 금감원 지시 항목 |
| S10 | 계약서 결제조건 ≠ 실제 송금방식 (L/C→T/T) | 기존 제품 사용 확인 0건 |
| S11 | 계약서 수익자명 ≠ 수취인명 | EU VoP와 중복 |
| S1 | 신규 수취계좌 | **트리거일 뿐 판별자 아님** — 정상 변경도 이력이 없음 |

S10은 **방향을 구분합니다.** T/T→L/C(더 안전한 방향)는 경고하지 않습니다.
무조건 경고하면 현장에서 게이트가 꺼집니다.

## 현재 베이스라인에서는 LLM 없이 성립하지 않습니다

S16은 `[계약이 허용한 경로] ∩ [이번 지시가 온 경로]`를 계산합니다.
오른쪽은 **폼 항목 1개**로 받으면 되지만(위 미확인 참조), **왼쪽은 계약서 자연어에만 있습니다.**

### 사람이 판독한 라벨과 대조한 유일한 혼동행렬 (개발셋 30건)

실물 계약서 **30건 전수 측정** ([`docs/05`](docs/05_베이스라인A_실측.md) · 원자료
`data/contracts/_baseline_result.json`):

| 조항 추출기 | n | TP | FP | TN | FN | 정확도 | Precision | Recall |
|---|--:|--:|--:|--:|--:|--:|--:|--:|
| 정규식 | 30 | 5 | 2 | 4 | 19 | 30.0% | 71.4% | **20.8%** |
| **LLM (gpt-4o-mini)** | 30 | 22 | 1 | 5 | 2 | **90.0%** | 95.7% | **91.7%** |

**측정 대상은 `amendment_clause_requires_written` 하나입니다** — S16이 이 비트로
**`BLOCK_PENDING`(하드 차단)과 `HOLD`(보류)를 가릅니다**. 정답은 사람이 계약서를 읽고
붙인 라벨(`data/contracts/_gold.json`)이고, 추출기는 그 라벨을 보지 못합니다.

> ⚠️ **이 수치의 성격을 정확히** — 세 가지를 구분해 적습니다.
>
> | | |
> |---|---|
> | 비순환인가 | ✅ 예. 라벨이 추출 결과에서 파생되지 않았습니다 — 아래 holdout 92.9%와 다른 점입니다 |
> | 독립 test set인가 | 🔴 **아닙니다.** **같은 30건으로 라벨을 정정하고 추출기를 고쳤습니다**(gold 라벨 8건 사후 정정, [`docs/05` §1](docs/05_베이스라인A_실측.md)). 개발셋 재대입 점수이므로 낙관 편향이 있습니다 |
> | 이 비트가 차단을 정하는가 | 🔴 **아닙니다.** 차단 *여부*가 아니라 **등급**을 가릅니다 — 비트 True→`R2/BLOCK_PENDING`, False→`R7/HOLD`. **둘 다 사람 승인이 필요**합니다. 일반 경로에서는 `notice_channels`·`notice_channel_types`·`registered_contact`도 등급에 관여합니다([`signals.py`](src/kb_payee_guard/signals.py)) |
>
> "유일한"은 **명시적 gold 파일로 혼동행렬을 낸 것이 이 하나**라는 뜻입니다.
> 다른 수기 대조는 더 있습니다 — 영문 검출 정밀도 16건 수기 판독, 국문 판정 전건 감사
> ([`MANIFEST.md`](data/contracts/MANIFEST.md)). 다만 그것들은 혼동행렬이 아닙니다.

정규식은 해석에서 지기 전에 **조항을 찾지 못합니다** — 오답 21건 중 19건이 미탐지.
조항이 표준 위치에 있지 않고 본문 문단에 섞여 있기 때문입니다.

**그렇다고 LLM에 판정을 맡기지는 않습니다.** 계약서·인보이스·메일은 전부 사기범이 작성할 수 있는
입력이라, LLM에 등급 결정권을 주면 문서에 삽입된 지시로 뚫립니다.

```
LLM  →  계약서에서 사실만 추출 (추출 스키마에 판정 칸이 아예 없음)
규칙 →  등급과 근거 문장 결정 (결정론 테이블 11개)
```

## 게이트가 실제로 무엇을 막고 무엇을 통과시키나

실물 계약서 30건에 **자체 설계 시나리오 5종**을 적용한 150건 전수 **기능시험**입니다
([`docs/06`](docs/06_E2E_탐지율_오탐률.md)). 실제 사건 데이터가 아니고, 독립 표본 30건이
아니라 **같은 계약서 30건의 반복 적용**입니다.

| 추출 경로 | 전체 공격 차단 | 위조 제외 차단 | 정상 시나리오 오차단 |
|---|--:|--:|--:|
| LLM | **62.2%** | 93.3% | 0.0% |
| 정규식 | 11.1% | 16.7% | 0.0% |

🔴 **두 열의 차이가 곧 이 게이트의 한계입니다.** 공격 3종 중 **수정합의서 위조**(계약서를
위조해 절차를 지킨 것처럼 꾸미는 공격)는 **30건 전건 미탐**입니다 — S16은 지시가 온 *경로*를
보지 문서의 *진위*를 보지 않기 때문입니다. 이 한 종을 빼면 93.3%, 넣으면 62.2%입니다.
**둘 다 적는 이유는 뒤 숫자만 적으면 무엇을 못 막는지가 사라지기 때문입니다.**

이 30건은 **규칙을 고치는 데도 쓴 데이터**입니다. 그래서 아래를 따로 측정했습니다.

### 🎯 Holdout — 규칙 튜닝에 한 번도 안 쓴 232건

저장소의 계약서는 262건인데 위 평가는 그중 30건만 씁니다.
**나머지 232건**(CUAD 46 · 무역 영문 62 · SEC 75 · ⚠️국문 조달서식 49)은 규칙 튜닝에 쓰인 적이
없습니다. 국문 49건은 송금 계약이 아니라 국내 조달 표준서식입니다 — 아래에서 따로 다룹니다.
같은 시나리오 5종을 그대로 합성해 돌렸습니다 — `scenarios.build()`는 정답 라벨이 아니라
계약서 사실에서 시나리오를 만들기 때문에 라벨 없는 계약서에도 그대로 적용됩니다.

🔴 **판정은 2분법이 아니라 3분법입니다.** 게이트는 `UNKNOWN`(판정 불가)도 **사람 승인 없이는
통과시키지 않습니다**(`gate.py` `_NEEDS_APPROVAL`, INV-5). 그래서 "차단/통과" 두 칸으로 적으면
**정상 거래에 생기는 마찰이 사라집니다.** 세 상태를 그대로 적습니다:

**정상 거래 464건이 어떻게 되는가**

|---|--:|--:|--:|
| gold · LLM (60건) | 93.3% | 6.7% | **0.0%** |
| gold · 완전추출 상한 (60건) | 100.0% | 0.0% | 0.0% |
| **holdout · LLM (464건)** | **75.0%** | **25.0%** | **0.0%** |
| holdout · 정규식 (464건) | 18.1% | 🔴 **81.9%** | 0.0% |

**공격 696건이 어떻게 되는가**

| 코퍼스 | 차단 | 보류(UNKNOWN) | **그냥 통과** |
|---|--:|--:|--:|
| gold · LLM (90건) | 62.2% | 6.7% | 31.1% |

- **"막았나"** — 하드 차단 오탐은 세 경우 모두 **0.0%**입니다. 정상 거래를 잘못 막지는 않습니다.
- **"현장에서 쓸 만한가"** — holdout에서 **정상 4건 중 1건이 사람에게 갑니다.** 이건 오탐은
  아니지만 **운영 비용**입니다. 정규식 경로는 82%가 사람에게 가서 **사실상 쓸 수 없습니다.**

> 🔴 이 표는 cross-model 리뷰(Codex GPT-5.6)가 잡아낸 것입니다. 직전 README는 오탐률만
> `0.0%`로 적어 **25% 수동검토를 숨기고 있었습니다.** 평가 코드의 `BLOCKING`이 `UNKNOWN`을
> 빼는데 제품의 `_NEEDS_APPROVAL`은 포함해서, **지표와 제품이 어긋나 있었습니다.**

위조 제외 기준 차단율은 gold 93.3% → holdout 75.0%, 전체 기준은 62.2% → 50.0%입니다.

생성된 합성 정상건 기준이라, **일반화가 확인됐다고는 말할 수 없습니다** (아래 holdout 절 참조).

### ⚠️ 국문 49건은 국문 무역계약 성능으로 읽을 수 없습니다 — 전건 미체결 표준서식

다만 *왜 비었는가*(문서 종류인가 한국어인가)는 아래처럼 확정하지 못했습니다.

> ① 송금 계약이 아니라서 ② 한국어 추출이 어려워서.
> 국문 49건이 **전부 표준 서식**이라 "국문이면서 송금 계약"인 표본이 사실상 0건입니다

> 유무*로만 가르면, **영문 안에서는** 당사자가 없어도 93.8% → 86.4%로 **7.4%p만** 떨어집니다.
> ①만으로는 8.2%가 설명되지 않습니다. 따라서 *"송금 계약이 아니라서"* 는 **가장 그럴듯한
> 설명이지 입증된 인과가 아닙니다.**

```bash
python3.12 scripts/recheck_holdout.py    # 위 표 전부 재집계 · API 키 불필요
```

> 🔴 **이 수치가 무엇을 재는지 정확히 적습니다.** holdout 232건에는 **정답 라벨이 없습니다.**
> `scenarios.build(facts, ...)`가 **추출된 사실로 시나리오를 만들기** 때문에, 추출이 틀렸어도
> `null`만 아니면 그 틀린 값에 맞춰 송금 요청이 생성되고 규칙은 "맞게" 발화합니다.
> 따라서 92.9%는 **독립 정답 대비 E2E 정확도가 아니라 "추출이 비지 않았을 때 규칙이 설계대로
> 발화하는가"** 입니다. **과적합 부재를 증명하지 않습니다** — 규칙 발화가 gold와 비슷한 수준이라는
> 것까지가 이 수치가 말할 수 있는 전부입니다.
>
> ✅ **비순환 대조는 따로 있습니다** — 등급을 가르는 비트(`amendment_clause_requires_written`)를
> 사람이 라벨링한 **개발셋** 30건과 대조했습니다: **정확도 90.0% · Precision 95.7% · Recall 91.7%**
> (TP 22 / FP 1 / TN 5 / FN 2, [위 혼동행렬](#사람이-판독한-라벨과-대조한-유일한-혼동행렬-개발셋-30건)).
> 🔴 그 30건도 **독립 test set은 아닙니다** — 같은 30건으로 라벨 정정과 추출기 개선을 했습니다.
> 즉 **입력 비트는 비순환으로 쟀고(단 개발셋), 종단 판정률은 아예 검증되지 않았습니다.** 둘을 섞어 읽지 마십시오.
>
> **대상/비대상 판정은 접두사가 아니라 문서별 매니페스트**(`data/contracts/_corpus_manifest.json`)가
> 정합니다. 기준은 *"체결 당사자가 채워졌는가"* 이고 **전 코퍼스에 동일 적용**합니다 — 영문
> 214건 중 비대상 판정은 0건입니다. 직전 구현은 `OFF_TARGET={"kr"}` 접두사 하드코딩이라
> 접두사만 늘리면 숫자가 올라가는 구조였습니다.

> 🔴 **국문 문제는 해결되지 않았습니다.** 위에서 바꾼 것은 *진단의 확실성*입니다 —
> *"국문이라서 무너진다"*(단정) → *"문서 종류일 가능성이 높으나 한국어 요인과 분리 불가"*.
> **실물 국문 무역계약서 0건**이라 국문 무역계약서 성능은 **측정된 적이 없고**, 그것을
> 확보하기 전에는 원인도 확정할 수 없습니다. 본선 최우선 과제입니다(로드맵 P10).
>
> 그래서 **232건 75.0%를 지우지 않았습니다.** 대상 문서군만 남기면 숫자는 좋아지지만,
> 제외 근거가 완전히 입증되지 않은 상태에서 낮은 쪽을 지우면 그건 데이터 고르기입니다.
> 두 줄을 다 두고 판단은 읽는 분께 맡깁니다.

정규식으로 추출하면 위조 제외 공격 464건 중 **위험 판정은 84건(18.1%)뿐이고 380건(81.9%)이
`UNKNOWN`** 입니다. **자동 통과는 0건**이라 뚫리지는 않지만, 정상 거래의 82%까지 승인 대기로
가므로 **현장에서 쓸 수 없습니다.**

**알려진 사각지대를 평가셋에서 빼지 않았습니다.** 사기범이 **수정 합의서를 위조**하면
통과합니다(30건 전건 미탐). S16은 지시의 *경로*를 보지 문서의 *진위*를 보지 않기 때문입니다.
통과할 것을 알면서 넣었습니다 — 빼면 숫자는 좋아지지만 심사에서 물었을 때 답이 없습니다.

그 계약서에서 조항을 실제로 추출해 판정합니다.

| | |
|---|---|
| 입력 | 텍스트 붙여넣기 (파일 선택기는 `.txt` / `.md` 를 권장 형식으로 걸어 두었을 뿐, **서버는 텍스트만 보고 확장자를 검사하지 않습니다**). PDF는 텍스트를 복사해 붙여 넣으세요 |
| 크기 | 200자 이상 · 최대 400KB |
| 추출 | 업로드 시 **1회만** 호출하고 캐시 — 시나리오를 바꿔도 재호출하지 않습니다 |
| 보관 | 원문·추출 결과 모두 **서버 프로세스 메모리에만**. 파일·DB 미기록, 서버를 끄면 사라짐 |

> 빈 사실은 전 항목 `UNKNOWN`이 되는데, 그러면 화면상으로는 *"판정했다"* 로 보이면서
> 실제로는 계약서를 한 글자도 읽지 않은 상태가 됩니다. 그 상태를 만들지 않으려고 막았습니다.

#### 판정 근거 전 과정 — 사람이 검증하는 영역

3번 카드에는 판정 등급 아래로 **계약서 사실과 규칙이 만든 값을 분리한** 감사 기록이 펼쳐집니다.
*"AI가 그렇게 판단했다"* 는 금융에서 근거가 아니기 때문에, 다음 사슬을 한 칸씩 되짚을 수 있게 했습니다:

> ⚠️ **키 없이 열면 2단계는 AI 추출이 아닙니다** — 사람이 옮겨 적은 고정 라벨이고 근거 구간은
> 0건입니다. 화면이 `facts_origin`에 따라 제목·열 이름을 바꿔 그 사실을 표시합니다.
> AI가 뽑은 값을 대조해 보시려면 설정에서 키를 넣으십시오. 3·4단계(신호·규칙)는 출처와 무관합니다.

```
계약서 원문 → 근거 구간 대조 → 추출된 사실 → 신호 산출 → 규칙 테이블 → 판정
```

| 단계 | 무엇이 보이나 | 만든 주체 |
|---|---|---|
| **1 · 사람이 입력한 값** | 계좌·BIC·금액·출처·발신자·스레드 — 폼에 넣은 그대로 | 사람 |
| **2 · 계약서에서 뽑은 사실** | 8개 항목의 값 + **근거 구간** (아래 단서 참조) | **LLM** 또는 수동 라벨 |
| **3 · 신호 산출** | 이 데모가 평가하는 **신호 9종 전부** — 발화하지 않은 것 포함 | 규칙 코드 |
| **4 · 규칙 테이블** | 규칙 **11개 전부**를 first-match 순서로, 적중 규칙 표시 | 규칙 코드 |

**2단계의 근거 구간**이 할루시네이션 검증의 축입니다. LLM이 계약서에서 **복사해 온 문장**이고,
`llm_extract._verify_spans`가 그 문장이 원문에 실재하는지 대조합니다. 화면 상단에
`근거 구간 N/M 확보` 로 표시되므로, 담당자는 2번 카드의 원문에서 찾아 눈으로 확인하면 됩니다.

> 🔴 **이 방어의 정확한 범위** — 과장하지 않고 적습니다.
>
> | | |
> |---|---|
> | LLM이 추출하는 값 필드 | **9개** (`llm_extract._SCHEMA`) |
> | 그중 근거를 **요구하는** 필드 | **4개** — 상대방명 · 소재국 · 결제조건 · §Amendment 조항 (`evidence_spans.required`) |
> | 나머지 5개(연락처 · §Notices 조항 · 통지경로 등) | ⚠️ 근거 검증 **대상이 아닙니다** |
> | 원문에 **없는 문장**을 써낸 경우 | 🔴 해당 필드를 **버립니다** — 이게 방어가 작동하는 유일한 경로입니다 |
> | 근거를 **`null`로 낸** 경우 | ⚠️ **버리지 않습니다** (`_verify_spans`의 `if not v: continue`). 값은 남고 근거 칸이 빕니다 |
> | 감사 화면의 **8행** | 스키마 9개와 **다릅니다** — 사람이 봐야 할 항목 기준이라 계약금액·"변경에 서면 요구"(파생값)를 넣고 일부 원본 필드를 뺐습니다 |
>
> 즉 **근거 칸이 빈 항목은 "검증된 값"이 아니라 "검증되지 않은 값"** 입니다.
> 화면이 그 사실을 숨기지 않고 빈칸으로 보여 주는 이유가 이것이고,
> **HITL이 필요한 지점도 정확히 여기**입니다. 전 필드 근거 강제는 미구현(P6)입니다.

3·4단계를 **발화하지 않은 것까지** 보여 주는 이유도 같습니다. 발화한 신호만 보여 주면
*"왜 이건 안 걸렸나"* 를 확인할 방법이 없어, 통과 판정을 사람이 검증할 수 없습니다.
다만 여기 나오는 9종은 **구현된 신호 전부**이고, 설계만 된 M3·M4·M6·M7·M8은 애초에 없습니다(P5).

> 화면 하단에 **담당자 확인 순서** 5단계가 함께 표시됩니다.
> 마지막 항목은 *"어긋나는 칸이 하나라도 있으면 승인하지 마시고 원본 서류로 확인하세요"* 입니다.

#### 화면에서 API 키 넣기 — 설정

우측 상단 **설정** 버튼에서 OpenAI 키를 넣으면, 그 다음 판정부터 계약서를
**실제 LLM으로 추출**합니다. 상단 배지가 `수동 라벨` → `LLM 추출` 로 바뀝니다.

```
설정 → API 키 입력 (sk-...) → 저장하고 LLM 추출 사용
```

🔒 **키를 다루는 방식** — 코드에서 확인 가능합니다(`scripts/demo_server.py`):

| | |
|---|---|
| 보관 위치 | **서버 프로세스 메모리에만** (`_session_key`) — 파일·DB 미기록 |
| 로그 | 등록 시 `"API 키 등록됨"` 한 줄만. **원문·마스킹값 모두 미기록** |
| 조회 응답 | `sk-…cdef` 형태로 **앞 3자 + 뒤 4자만** 반환 |
| 브라우저 | localStorage·쿠키 미사용. 입력 직후 필드를 비웁니다 |
| 수명 | 서버를 끄면 사라짐 · **지우기** 버튼으로 즉시 삭제 |
| 실패 시 | LLM 추출이 실패하면 자동으로 수동 라벨로 되돌아가고 화면에 표시 |

키가 없으면 같은 계약서를 **사람이 읽고 옮겨 적은 값**으로 판정하며, 매 판정마다
**어느 경로를 썼는지 화면에 표시**합니다. 환경변수 `OPENAI_API_KEY`가 이미 있으면
그것을 쓰고, 화면 입력이 그보다 우선합니다.

> 🔴 **은행 연동도 프로덕션 REST API도 아닙니다.** 판정 엔진을 눌러 보는 **로컬 확인용
> 사이트**입니다 — 인증·영속·감사원장·동시성 처리가 없고 `127.0.0.1`에만 바인딩합니다.
> 화면은 판정 엔진을 눌러 보게 하는 것이 전부이고, **외부 REST API·은행 시스템 연동은
> 여전히 미구현(P7)** 입니다.

### 2단계 — OpenAI API 키를 넣고 LLM 추출까지 재현하기

**1단계는 키가 필요 없습니다.** 여기부터는 계약서에서 조항을 실제로 뽑는 경로(C)라
OpenAI 키가 필요합니다. 아래 그대로 따라 하시면 됩니다.

#### ① 키 발급

[platform.openai.com/api-keys](https://platform.openai.com/api-keys) → **Create new secret key**
→ `sk-` 로 시작하는 문자열을 복사합니다. (결제수단 등록이 되어 있어야 호출이 됩니다.)

#### ② 키 등록 — 둘 중 편한 쪽

```bash
# 방법 1. 저장소 루트에 .env 파일  (권장 — .gitignore 에 있어 커밋되지 않습니다)
cd kb-payee-guard
echo 'OPENAI_API_KEY=sk-여기에-키를-붙여넣으세요' > .env

# 방법 2. 환경변수  (현재 셸에서만 유효)
export OPENAI_API_KEY="sk-여기에-키를-붙여넣으세요"
```

> 🔒 `.env` 는 `.gitignore` 에 등재되어 있습니다 — `git check-ignore -v .env` 로 확인 가능합니다.
> 키를 코드나 커밋에 넣지 마세요.

#### ③ 등록 확인

```bash
python3.12 -c "import os,pathlib
[os.environ.setdefault(*l.split('=',1)) for l in pathlib.Path('.env').read_text().splitlines() if '=' in l]
k=os.environ.get('OPENAI_API_KEY','')
print('✅ 키 인식됨' if k.startswith('sk-') else '🔴 키 없음')"
```

#### ④ 실행

```bash
python3.12 scripts/run_baselines.py --with-c              # 추출 정확도 A vs C  (30건 · 약 1분)
python3.12 scripts/run_e2e.py --extract C                 # 탐지율·오탐률       (150건 · 약 3분)
python3.12 scripts/run_e2e.py --corpus holdout --extract C # holdout 재측정      (232건 · 약 10분)
```

#### 💰 비용 — 생각보다 훨씬 쌉니다

| 실행 | 계약서 | 실제 전송 | 비용 |
|---|--:|--:|--:|
| `run_baselines.py --with-c` | 30 | 0.4 MB | **약 $0.02** |
| `run_e2e.py --extract C` | 30 | 0.4 MB | **약 $0.02** |
| `run_e2e.py --corpus holdout --extract C` | 232 | 2.9 MB | **약 $0.17** |

계약서를 통째로 보내지 않기 때문입니다 — `max_chars=24,000` 으로 **§Notices·§Amendment
주변만 발췌**해 보냅니다. 390KB 계약서도 24K자만 전송되고, 원본 12.8MB 중 **22%만** 나갑니다.
모델은 `gpt-4o-mini`(입력 $0.15/1M · 출력 $0.60/1M)입니다.
`[추정]` — 실측 전송 문자수 × 4자/토큰 가정 × 공개 단가. 정확한 값은 OpenAI Usage 페이지에서 확인하세요.

#### 키가 없거나 잘못됐을 때

조용히 잘못된 결과를 내지 않고 **멈춥니다**:

```
LLMProviderError: no API key (set OPENAI_API_KEY or OPENAI_KEY_FILE)
```

> **1단계 128건은 키 없이 그대로 통과합니다.** 승인 게이트 · 인젝션 방어 · dead rule 검사 등
> **결정론 로직의 불변식**은 전부 1단계에서 검증됩니다.
>
> 🔴 **다만 128건은 LLM 경로의 신뢰성을 검증하지 않습니다.** 전부 가짜 transport를 주입해
> 네트워크를 타지 않기 때문입니다(`test_extracts_without_network`). 그래서 아래는 **키를
> 넣고 실제로 돌리기 전까지 알 수 없었습니다** — 실제로 이번에 전부 그렇게 발견했습니다:
>
> | 실제 실행에서만 드러난 것 | 128건이 못 잡는 이유 |
> |---|---|
> | 계약서 1건(`sec-047`)이 **항상 타임아웃** | stub은 즉시 응답 — 지연이 없음 |
> | 재시도가 없어 **1건 실패로 232건 전량 손실** | stub은 실패하지 않음 |
> | **국문 조달서식 8.2%** | stub은 고정 응답 — 추출 품질을 보지 않음 |
>
> **"테스트가 통과한다"와 "실제로 동작한다"는 다릅니다.** 이 저장소에서는 전자만 키 없이
> 확인되고, 후자는 위 2단계를 직접 돌려야 확인됩니다.

> ⚠️ `run_e2e.py`는 실행할 때마다 결과 파일을 덮어씁니다 —
> `--corpus gold` 는 `_e2e_result_{gold,A,C}.json`, `--corpus holdout` 은 `_e2e_holdout_{A,C}.json` 입니다
> (추출기별로 분리되어 A 결과를 C 실행이 덮지 않습니다).
> 커밋된 `_e2e_result_gold.json` 이 gold facts(추출 완벽 시 상한) 결과입니다.

## 설계 원칙

| 원칙 | 내용 |
|---|---|
| 켜지 않아도 작동 | 별도 앱이 아니라 **송금 신청 흐름 안**에 있음 |
| 판정이 아니라 대조 | 확률을 말하지 않음. *"계약서에 뭐라 적혔고 이번 송금은 어떻다"* 만 말함 |
| 추가 서류 요구 0 | 계약서가 이미 증빙으로 제출된 거래에 한함 (계약서가 항상 필수는 아님) |
| LLM은 판정하지 않음 | 등급은 규칙 테이블이 결정 — 프롬프트 인젝션 방어 |
| 계약 체결 시점이 신뢰 기준 | 은행 보관 원본의 §Notices·§Amendment는 사후 변경이 어려움. **새 수정합의서 위조는 별개 — 전건 미탐** |
| 모든 규칙은 발화해야 함 | 입력이 없는 규칙은 배포 금지 — 도달성 전수 검사 |

**튜닝할 계수가 없습니다.**

```
❌ "이 변경은 사기 확률 87%"                              → 정답 라벨 필요, 가중치 튜닝 필요
✅ "계약서 §14는 서면 합의를 요구하는데 이번 지시는 이메일"  → 두 문서에서 직접 나오는 사실
```

규칙의 **조건이 곧 사용자에게 보이는 문장**입니다. 조정할 가중치도 임계값도 없습니다.
대신 **공격 테스트 16종**으로 *"이 조합은 대조로 걸린다"* 를 증명합니다.

> 단 *"평가가 필요 없다"* 는 뜻은 아닙니다. 판정이 결정론이어도 **입력(계약서 추출)이 틀리면
> 결과는 확정적으로 틀립니다.** §Notices·§Amendment 추출 정확도가 시스템 정확도의 상한입니다.

| 층 | 내용 | 상태 |

| 안전 | 인젝션 3중 방어 · 근거 구간 원문 대조 (**4개 필드 한정** — [범위](#판정-근거-전-과정--사람이-검증하는-영역)) | 🟡 |

**승인 게이트는 코드로 강제합니다.** 게이트 함수는 승인 *객체*를 받지 않고 **`approval_id` 문자열만**
받아 원장을 조회합니다. 모델이 승인을 위조하려면 원장에 써야 하는데, 원장에 쓰는 유일한 경로는
**허용된 채널 값으로 호출하는 발급 함수**입니다. 공격 테스트 T1~T5·T10·T11이 이를 검증합니다.

> 🔴 **구현 수준을 정확히**: 코드가 검증하는 것은 **채널 enum · 건별 ID 결박 · TTL**입니다.
> **사람이 실제로 확인했는지는 인증하지 않습니다** — `approved_by`는 임의 문자열입니다.
> 감사 로그도 `append-only` 인터페이스일 뿐 **영속·변조방지 원장이 아닙니다**(메모리 리스트).
> 실제 신원 인증과 변조방지 원장은 본선 과제입니다.

> **L5는 미구현입니다.** 현재 사용자에게 나가는 근거 문장은 규칙이 만든 결정론 문자열입니다
> (아래 실행 예시의 출력이 그것입니다). LLM 서술을 붙이면 표현은 자연스러워지지만
> **문서에 삽입된 지시가 사용자 설명까지 오염시킬 경로가 생기므로**, 인젝션 방어를 먼저
> 검증한 뒤 붙입니다 — 미룬 것이지 빠뜨린 것이 아닙니다.

> **R10은 없습니다** — 2026-08-02에 제거했습니다. S1(신규 계좌) 단독 차단이
> **정당한 계좌 변경을 100% 막았기** 때문입니다. 실제 규칙은 11개입니다.
