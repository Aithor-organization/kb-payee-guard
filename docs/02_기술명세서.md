## 1. 시스템 개요

### 1.1 한 문장

**해외송금 신청 시 법으로 이미 제출되는 계약서를 읽어, 수취계좌 개설국·결제방식이 계약과 어긋나면 사람이 확인하기 전까지 송금을 보류한다.**

### 1.2 v2 → v3 설계 축 전환

| | v2 | **v3** |
|---|---|---|
| 핵심 입력 | 과거 송금 계좌 이력 (은행 내부 DB) | **법정 제출 계약서** |
| 핵심 신호 | S1 신규 계좌 감지 | **S9 소재국 불일치 · S10 결제조건 불일치** |
| S1 역할 | 판별 신호 | **트리거로 강등** |
| 내부 API 의존 | 있음 (U-11) | **없음** |
| 판정 성격 | *"평소와 다르다"* | ***"계약서와 다르다"*** |

**전환 이유**: 정당한 계좌 변경도 신규 계좌다. S1만으로는 사기와 정당한 변경을 구분할 수 없다. 반면 **계약서와의 불일치는 문서로 증명되는 사실**이다.

### 1.3 시스템 경계

```
[송금 신청]  ────────▶ ┌─── KB Payee Guard ──────────────────┐
 · payee 정보           │  L0 입력 검문 (PII·인젝션)   guard   │
 · new_account          │       ↓                              │
 · amount               │  L1 계약서 판독            LLM 허용  │
 · 계약서 (법정 제출)    │       ↓                              │
 · 인보이스              │  L2 계약서 ↔ 송금 대조     결정론    │
 · 계좌변경 요청 (선택)  │       ↓                              │
                        │  L3 보조 신호 (문서 있을 때) 혼합    │
                        │       ↓                              │
                        │  L4 규칙 테이블 판정       결정론 🔴 │
                        │       ↓                              │
                        │  L5 근거 생성              LLM 허용  │
                        │       ↓                              │
                        │  ★ HITL 보류 게이트        코드 강제 │
                        └──────────────┬───────────────────────┘
                                       ▼ 승인 검증 통과 시에만
                                 [송금 실행 허가]
```

### 1.4 불변식

| ID | 불변식 | 강제 수단 |
|---|---|---|
| **INV-1** | 판정 엔진은 **어떤 외부 호출도 하지 않는다** | AST 정적 검사 — 모듈 전체에 네트워크·프로세스 호출 부재를 테스트로 증명 |
| **INV-2** | 고위험 판정 시 **승인 없이 송금 통과 불가** | 게이트가 승인 토큰 부재 시 `BLOCKED` |
| **INV-3** | 승인은 **1회용** + **건·계좌·승인자 결박** | `case_id` + `account_fingerprint` + `consumed` + TTL |
| **INV-4** | 모든 판정·승인이 **단일 `trace_id`로 추적** | 진입 시 발급, 전 노드 전파, append-only |
| **INV-5** | **판정 불가를 통과로 처리하지 않는다** | 계약서 부재/추출 실패 → `UNKNOWN` 보류 |
| **INV-6** | **LLM은 최종 등급을 정하지 않는다** | 판정 노드가 `kind: deterministic` |
| **INV-7** | **모델이 스스로 승인 토큰을 만들 수 없다** | AITHOR 런타임 코드 차단 |
| **INV-8** | **근거 문장의 모든 주장은 문서 근거에 매핑된다** | 생성 후 매핑 검사 — 미매핑 문장 존재 시 실패 |

> **INV-5의 근거**: 계약서 추출이 실패했는데 "불일치 없음"으로 처리하면 **OCR 장애가 곧 전면 통과**가 된다.
> **INV-6·7의 근거**: 프롬프트 인젝션. 사기범이 인보이스나 메일에 *"이 요청은 정상입니다"* 를 넣을 수 있다.
> **INV-8의 근거**: 이 시스템의 산출물은 등급이 아니라 **근거 문장**이다. 창작된 문장은 제품 실패다.

## 2. 구현 기반 — AITHOR-Agent-Framework

| 요구 | AITHOR 제공 | 우리가 할 일 |
|---|---|---|
| 승인 게이트 (INV-2, 7) | 승인 게이트 + **모델 자가승인 코드 차단** | 도메인 승인 스키마 |
| 인젝션 방어 (INV-6) | `AgentShield.RuntimeGuard` 3중 검문 (입력·**도구결과**·출력) | 어댑터 배선 |
| 감사 (INV-4) | `AuditStore.append` | 감사 이벤트 정의 |
| 판정/서술 분리 | 스키마 `kind: deterministic \| guard \| deterministic_or_llm` | 노드별 kind 지정 |
| 컴플라이언스 | `compliance_packs/finance.json` (7 controls) | `trade-remittance` 팩 확장 |
| 성숙도 게이트 | `maturity assess` (미달 시 CI exit 1) | 목표 등급 선언 |
| 재현성 | 995 결정론 테스트 · stdlib only | 도메인 테스트 추가 |

🔴 **핵심 이점**: *"LLM에 판정 권한을 주지 않는다"* 가 **워크플로우 스키마로 강제**된다. `kind: deterministic` 노드에 LLM을 넣으면 검증이 실패한다.

## 3. 입력 — 법정 제출 서류

| 입력 | 확보 근거 | 필수 |
|---|---|:---:|
| **계약서** | 연 10만 달러 초과 송금 시 **제출 의무** (외국환거래법) | ✅ |
| 인보이스 (commercial invoice) | 수입대금 송금 증빙 | ✅ |
| 송금 신청 정보 (수취인·계좌·금액·송금방식) | 송금 신청서 | ✅ |
| 🎯 **계좌 지시 출처** (`AccountInstruction`) | **은행이 신청 필드로 묻는다** — S16 입력 | ✅ |
| 🎯 **거래처 과거 수취계좌 이력** | **은행이 이미 보유·운영** ([E-6](00_조사노트.md) *"같은 계좌가 표시된 외화송금확인서"*) — S1 트리거 입력 | ⭕ |
| 계좌변경 요청 문서 (메일 등) | 사용자 임의 제출 | ❌ |

```python
class InstructionSource(str, Enum):
    """이 계좌를 어디서 받았는가."""
    CONTRACT   = "contract"      # 계약서에 명시된 계좌
    AMENDMENT  = "amendment"     # 계약 수정 합의서
    INVOICE    = "invoice"       # 인보이스 기재
    PORTAL     = "portal"        # 상대방 공식 포털·시스템
    EMAIL      = "email"         # 이메일 통보
    PHONE      = "phone"         # 전화 통보
    FAX        = "fax"           # 팩스
    OTHER      = "other"

class AccountInstruction(BaseModel):
    """S16 입력. 🎯 은행이 송금 신청 시 필수로 묻는다 — 사용자 능동성 0."""
    source: InstructionSource
    channel_detail: str | None      # 발신 주소·전화번호 등
    document: Document | None       # 근거 문서 (있으면)

class RemittanceRequest(BaseModel):
    case_id: str
    payee_name: str
    payee_id: str
    new_account: Account            # IBAN 또는 계좌번호 + BIC
    amount: Money
    remittance_type: RemittanceType # TT | LC | DP | DA | ...
    contract: Document | None       # None = UNKNOWN 경로 (INV-5)
    invoice: Document | None
    account_instruction: AccountInstruction   # 🎯 필수 — S16
    payee_history: list[Remittance] | None    # 🎯 None = 조회 실패, [] = 신규 거래처
    change_request: Document | None            # 선택
```

🔴 **`contract is None`과 추출 실패를 구분한다.** 둘 다 `UNKNOWN`이지만 감사 로그에 사유를 다르게 남긴다.

🔴 **v3.1 정정 (독립 심사 지적)**: v3.0은 `payee_history`와 `account_instruction`이 입력 스키마에 **없었다.**
그 결과 ① S1을 참조하는 R7·R8이 **입력원 없는 dead rule**이 되고 ② 데모 D8(*"이름 일치, 계좌만 다름"*)이 **도달 불가**였다. **최빈 BEC**(같은 국가·같은 이름·같은 결제조건, 계좌만 교체)에 v3.0 규칙 전부가 침묵했다.
E-6이 *"같은 계좌가 표시된 외화송금확인서"* 로 **은행이 이력을 이미 보유함**을 증명하므로, U-11은 막힌 병목이 아니었다 — 우회할 필요가 없었다.

## 4. 판정 엔진

### 4.1 L1 — 계약서 판독 (LLM 허용, 추출 전용)

```python
class ContractFacts(BaseModel):
    """계약서에서 추출하는 사실. 판정·점수 필드가 존재하지 않는다 (INV-6)."""
    counterparty_name: str | None
    counterparty_country: str | None      # ISO 3166-1 alpha-2
    counterparty_address: str | None
    registered_contact: list[str]         # 계약서 기재 연락처
    payment_terms: PaymentTerms | None    # LC | TT | DP | DA | CAD | COD | ...
    payment_terms_raw: str | None         # 원문 그대로
    contract_date: str | None
    contract_amount: Money | None
    notice_clause: str | None             # 통지 조항 (있으면)
    evidence_spans: dict[str, str]        # 각 필드 → 근거 원문 구간 (INV-8)
```

**추출 대상 근거** — 한국무역협회 표준 무역계약서 서식에 결제조건 항목이 존재하며, 국제계약서에 당사자 주소 기재는 표준이다 ([조사노트 E-11](00_조사노트.md)).

🔴 **`evidence_spans` 필수**: 각 추출 필드가 계약서 어느 구간에서 나왔는지 기록한다. 없으면 창작이다.

**추출 실패 처리**:
```python
if facts.counterparty_country is None and facts.payment_terms is None:
    return ExtractionResult(failed=True, reason="no_extractable_fields")  # → UNKNOWN
```

### 4.2 L2 — 계약서 ↔ 송금 정보 대조 (결정론, LLM 없음)

**이 층이 v3의 핵심이다.** 문서 두 개를 비교하는 순수 함수다.

| ID | 신호 | 판정 로직 | 신규성 |
|---|---|---|---|
| 🎯 **S9** | `CONTRACT_COUNTRY_MISMATCH` | `contract.counterparty_country != iban_country(new_account)` | **금감원 지시 항목** |
| 🎯 **S10** | `PAYMENT_TERMS_MISMATCH` | `contract.payment_terms != request.remittance_type` | **기존 제품 사용 확인 0건** |
| **S11** | `BENEFICIARY_NAME_MISMATCH` | `normalize(contract.counterparty_name) != normalize(request.payee_name)` | VoP와 중복 |
| **S12** | `AMOUNT_EXCEEDS_CONTRACT` | `request.amount > contract.contract_amount` (허용 오차 내) | — |

```python
def iban_country(acct: Account) -> str | None:
    """IBAN 앞 2자리 = ISO 3166-1 alpha-2 (ISO 13616-1).
    IBAN 미사용국(미국 등)은 SWIFT BIC 5~6번째 자리로 대체."""
```

**S9·S10의 근거는 문서에 있다** — 추론이 아니다. 따라서 **정답 라벨(평가셋)이 필요 없다.**

#### S10 판정 표 — 위험 방향이 비대칭이다

| 계약서 결제조건 | 실제 송금 | 판정 | 이유 |
|---|---|---|---|
| **L/C** | **T/T** | 🔴 **고위험** | L/C는 은행 지급보증, T/T는 계좌 직입금. **사기범이 유도할 구조적 동기** |
| L/C | D/P·D/A | 🟡 중위험 | 보증 약화 |
| D/A·D/P | T/T | 🟡 중위험 | 서류 통제 상실 |
| T/T | T/T | ⚪ 일치 | — |
| T/T | L/C | ⚪ 저위험 | **더 안전한 방향** — 경고 불필요 |

🔴 **방향을 구분한다.** 안전한 쪽으로의 변경(T/T → L/C)은 경고하지 않는다. 무조건 경고하면 게이트가 꺼진다.

### 4.2-bis 🎯 S16 — 계좌 지시 출처 검증 (v3.1 신설, **판정 축의 중심**)

**독립 심사 처방**: *"신호의 극성을 뒤집어라 — 불일치를 찾는 대신 **계좌 지시의 출처 증명을 요구**하라."*

#### 왜 이것이 최빈 케이스를 잡는가

전형 BEC는 **같은 국가·같은 이름·같은 결제조건**에서 계좌번호만 교체한다. S9·S10·S11이 전부 침묵한다.
그런데 **경로는 반드시 다르다** — 사기범 메일은 계약서에 기재된 통지 경로가 아니다.

> **계약서 §Notices의 통지 경로는 계약 체결 시점에 확정되어 사기범이 사후에 바꿀 수 없다.**
> 이 비대칭이 S16의 전부다.

| ID | 신호 | 판정 |
|---|---|---|
| 🎯 **S16** | `ACCOUNT_INSTRUCTION_PROVENANCE` | `account_instruction.source`가 계약서 §Notices / §Amendment가 정한 경로를 따르는가 |

**판정 표**:

| 계약서 절차 조항 | 지시 출처 | 판정 |
|---|---|---|
| (조항 무관) | `CONTRACT` — 계약서 명시 계좌 | ⚪ 통과 |
| *"변경은 서면 합의로만"* | `AMENDMENT` — 수정 합의서 제출 | ⚪ 통과 |
| *"변경은 서면 합의로만"* | `EMAIL` · `PHONE` · `FAX` | 🔴 **고위험** — 조항 위반 |
| §Notices가 지정 이메일 명시 | `EMAIL` + 발신주소가 **지정 주소와 일치** | 🟡 중위험 |
| §Notices가 지정 이메일 명시 | `EMAIL` + 발신주소 **불일치** | 🔴 **고위험** |
| 절차 조항 **없음** | `EMAIL` · `PHONE` | 🟡 중위험 (조항 부재 → 근거 약함, 침묵하지 않음) |
| (조항 무관) | `INVOICE` 단독 | 🟡 중위험 — **인보이스는 위조 가능** |

```python
def assess_provenance(instr: AccountInstruction,
                      facts: ContractFacts) -> ProvenanceVerdict:
    """계약서 절차 조항 vs 지시 출처. 조항 해석은 L1에서 이미 추출됨."""
    if instr.source in (InstructionSource.CONTRACT, InstructionSource.AMENDMENT):
        return ProvenanceVerdict(severity="none")
    if facts.amendment_clause_requires_written and instr.source in (
        InstructionSource.EMAIL, InstructionSource.PHONE, InstructionSource.FAX
    ):
        return ProvenanceVerdict(severity="high", violated=facts.amendment_clause)
    if facts.notice_channels and instr.source == InstructionSource.EMAIL:
        ok = instr.channel_detail in facts.notice_channels
        return ProvenanceVerdict(severity="medium" if ok else "high")
    return ProvenanceVerdict(severity="medium", reason="no_procedure_clause")
```

#### S16이 닫는 결함 4개

| 결함 | 해소 |
|---|---|
| 최빈 케이스 침묵 | **경로가 다르므로 발화** — 국가·이름·조건과 무관 |
| **사용자 능동성 요구** (M1·M6은 사용자가 메일을 올려야 발화) | **은행이 신청 필드로 묻는다** → 능동성 0. 설계 원칙 ①과 정합 |
| **LLM이 교체 가능한 파서** | 🎯 **계약 절차 조항 해석이 판정 축으로 올라온다** — 전처리가 아님 |
| 은행 내부 이력 의존 | S16은 이력을 보지 않는다 |

🔴 **`ContractFacts` 확장 필요** (L1):
```python
    notice_clause: str | None
    notice_channels: list[str]                    # §Notices 지정 경로·주소
    amendment_clause: str | None
    amendment_clause_requires_written: bool       # "서면 합의로만" 여부
```

**조항 부재 시**: `severity="medium"` + 사유 `no_procedure_clause`를 감사 로그에 남긴다 (`TR-SIGNAL-HONESTY`). **침묵하지 않는다** — 조항이 없다는 것 자체가 근거 부재이므로 보류가 옳다.

### 4.3 L3 — 보조 신호 (계좌변경 요청 문서 제출 시만)

문서가 **없어도 L1·L2는 정상 동작한다** (D5 시나리오 — 전화·팩스 경로).

**결정론 신호**:

| ID | 신호 | 판정 |
|---|---|---|
| M1 | `DOMAIN_LOOKALIKE` | 계약서 기재 도메인 대비 편집거리 · homoglyph · TLD 치환 · IDN |
| M2 | `REPLY_CHAIN_BREAK` | `In-Reply-To` / `References` 헤더 단절 |
| M3 | `FREEMAIL_SHIFT` | 기업 도메인 → 무료 메일 |
| M4 | `DISPLAY_SPOOF` | 표시 이름 동일 · 실제 주소 상이 |

> **M1이 강화되었다**: v2는 "기존 거래 도메인"과 비교했는데 그 이력이 필요했다. v3는 **계약서 기재 연락처/도메인**과 비교한다 — 이력 불필요.

**LLM 신호**:

| ID | 신호 | 왜 LLM인가 |
|---|---|---|
| M6 | `URGENCY_PRESSURE` | *"감사 때문에 급하다"* 류 압박 맥락. 키워드 매칭은 정상 업무 문장을 다 걸린다 |
| M7 | `PRETEXT_PATTERN` | 계좌 변경 사유의 전형성 |
| **M8** | `NOTICE_CLAUSE_VIOLATION` | 계약서 통지 조항이 있을 때, 이 요청이 그 방법을 따랐는가 — **규칙으로 불가능** |

> M8은 `contract.notice_clause`가 존재할 때만 활성. 없으면 비활성 + 감사 기록 (신호 정직성).

🔴 **v3.1 — M8과 S16의 관계**: 둘 다 계약서 통지 조항을 본다. 차이는 **입력**이다.

| | M8 | **S16** (§4.2-bis) |
|---|---|---|
| 입력 | `change_request` 문서 (**선택** — 없으면 비활성) | `account_instruction.source` (**필수** — 은행이 항상 묻는다) |
| 판정 | LLM (요청 문서가 조항을 따랐나) | 결정론 (경로 자체가 조항 위반인가) |
| 커버 | 문서 제출 시만 | **항상** |

→ **S16이 상위 신호**다. M8은 문서가 제출된 경우의 **보강**으로 남긴다 (제거 안 함 — 문서 내용의 정황은 LLM만 읽는다).

**S1 (트리거)**: `request.payee_history`가 입력원이다 (§3).

| `payee_history` | 의미 | S1 |
|---|---|---|
| `None` | 조회 실패 / 미연동 | 비활성 + 감사 기록 |
| `[]` | 신규 거래처 (송금 이력 0) | 비활성 (신규는 "변경"이 아니다) |
| `[...]` 중 `new_account` 미포함 | **계좌 변경** | ✅ 발화 → R9/R10 |
| `[...]` 중 `new_account` 포함 | 기존 계좌 | 비활성 |

🔴 이력이 **있어도 트리거일 뿐 판별자가 아니다** — 정상 변경도 이력이 없다 (§E-8). 판별은 S16·S9·S10·S11이 한다. 이력이 **없어도** 계약서 대조만으로 판정한다 (v2와 달리 이력이 전제가 아니다).

### 4.4 L4 — 규칙 테이블 판정 (결정론)

| 규칙 | 조건 | 등급 | 커버 |
|---|---|---|---|
| **R1** | 계약서 부재 또는 추출 실패 | `UNKNOWN` | 장애 |
| 🎯 **R2** | `S16` **고위험** (계약 절차 조항 위반 경로) | `BLOCK_PENDING` | **최빈 BEC** |
| **R3** | `S9` (소재국 불일치) | `BLOCK_PENDING` | 국가 이동형 |
| **R4** | `S10` 고위험 방향 (L/C→T/T) | `BLOCK_PENDING` | 결제방식 전환형 |
| **R5** | `S11` (수익자명 불일치) | `BLOCK_PENDING` | 제3자 수취형 |
| **R6** | `M1` (도메인 유사 공격) | `BLOCK_PENDING` | 메일 제출 시 |
| 🎯 **R7** | `S16` **중위험** (조항 부재 또는 인보이스 단독) | `HOLD` | **근거 약함** |
| **R8** | `S10` 중위험 **OR** `S12` (금액 초과) | `HOLD` | — |
| **R9** | `S1` (신규 계좌) **AND** (`M2` **OR** `M6` **OR** `M8`) | `HOLD` | 보강 신호 |
| **R10** | `S1` (신규 계좌, 보강 신호 없음) | `HOLD` | 이력 기반 |
| **R11** | 계약서 일치 **AND** 고위험 관할 | `NOTICE` | — |
| **R0** | 전부 일치 | `PASS` | — |

**평가 순서**: R1 → R2 → … → R11 → R0 (first-match wins)

```python
RULES = [
    Rule("R1",  lambda s: s.extraction_failed,                     "UNKNOWN"),
    Rule("R2",  lambda s: s.S16_severity == "high",                "BLOCK_PENDING"),  # 🎯 최빈
    Rule("R3",  lambda s: s.S9,                                    "BLOCK_PENDING"),
    Rule("R4",  lambda s: s.S10_severity == "high",                "BLOCK_PENDING"),
    Rule("R5",  lambda s: s.S11,                                   "BLOCK_PENDING"),
    Rule("R6",  lambda s: s.M1,                                    "BLOCK_PENDING"),
    Rule("R7",  lambda s: s.S16_severity == "medium",              "HOLD"),           # 🎯
    Rule("R8",  lambda s: s.S10_severity == "medium" or s.S12,     "HOLD"),
    Rule("R9",  lambda s: s.S1 and (s.M2 or s.M6 or s.M8),         "HOLD"),
    Rule("R10", lambda s: s.S1,                                    "HOLD"),
    Rule("R11", lambda s: s.S5,                                    "NOTICE"),
    Rule("R0",  lambda s: True,                                    "PASS"),
]
```

🔴 **v3.1 정정 — dead rule 제거**: v3.0의 R7·R8은 `s.S1`을 참조했으나 **입력 스키마에 이력 필드가 없어 절대 발화하지 않았다.** §3에 `payee_history`를 복원해 R9·R10이 실제로 동작한다.

**최빈 BEC 커버리지 검증** (같은 국가·같은 이름·같은 결제조건, 계좌만 교체):

| 규칙 | v3.0 | **v3.1** |
|---|---|---|
| R2 `S16` | (없음) | 🎯 **발화** — 사기범 메일은 계약 절차 경로가 아니다 |
| R3 `S9` | 불발 (DE=DE) | 불발 |
| R4 `S10` | 불발 (T/T=T/T) | 불발 |
| R5 `S11` | 불발 (이름 일치) | 불발 |
| R10 `S1` | 🔴 **dead** | **발화** (이력 복원) |
| **결과** | 🔴 **전부 침묵** | ✅ **R2에서 차단** |

**등급별 동작**:

| 등급 | 화면 | 게이트 |
|---|---|---|
| `PASS` | 표시 없음 | 통과 |
| `NOTICE` | 1줄 안내 | 통과 |
| `HOLD` | 근거 + 확인 절차 | **보류** — 확인 버튼으로 해제 |
| `BLOCK_PENDING` | 근거 + 확인 절차 | **보류** — 담당자 승인 필수 |
| `UNKNOWN` | *"판정 불가"* 명시 | **보류** |

🔴 **가중합을 쓰지 않는 이유**: ① 데이터 없이 계수를 정할 수 없다 ② *"R2에 걸렸습니다"* 는 감사 대응이 되지만 *"0.87"* 은 안 된다 ③ **규칙 조건이 곧 사용자에게 보여줄 문장이다.**

### 4.5 L5 — 근거 생성 (LLM, 서술 전용)

```
❌ "위험도 87%"
✅ "제출하신 계약서(2023-04-11 체결)의 상대방은 독일 슈투트가르트 소재
    BAUER GmbH입니다. 이번 수취계좌는 리투아니아에서 개설된 계좌입니다.

```

| `TR-NO-GUARANTEE` | 안전 보장 문구 금지 |
| **`TR-NO-PERF-CLAIM`** | **측정하지 않은 성능 수치(탐지율·오탐률·정확도)를 문서·화면에 기재 금지** |

> 총 **13 controls** + 규제 근거 2건(금감원 지시 · 외국환거래법) 매핑. 각 control은 `surface`(코드 지점)와 `invariant`(불변식 ID)에 연결된다.

## 11. 평가

### 11.1 🎯 판정 규칙에 계수 튜닝이 필요 없다

> 🔴 **v3.1 정정**: v3.0은 이 절 제목이 *"평가셋이 필요 없는 구조"*였다. **과장이다.** 없어도 되는 것은 **판정 계층의 정답 라벨**이지, 평가 전체가 아니다. 판정이 결정론이어도 **입력(L1 추출)이 틀리면 결과는 확정적으로 틀린다** — *garbage in, deterministic garbage out*.

우리는 **확률 판정을 하지 않는다.** 두 문서를 비교해 **참/거짓**을 말한다. 그래서 **가중치·임계값을 튜닝할 대상이 없다**.

| 계층 | 항목 | 정답 라벨 필요? |
|---|---|:---:|
| **판정 (L2·L4)** | S9 소재국 (문자열 비교) | ❌ |
| | S10 결제조건 (열거형 비교) | ❌ |
| | S11 수익자명 (정규화 후 비교) | ❌ |
| | **S16 지시 출처** (열거형 + 조항 대조) | ❌ |
| | 규칙 테이블 R1~R11 | ❌ 조건이 곧 사용자 문장 |
| **입력 (L1)** | 🔴 **계약서 항목 추출 정확도** | ✅ **필요** — 서식 샘플 세트 |
| | 🔴 **`notice_channels` / `amendment_clause` 추출** | ✅ **필요** — S16의 생사가 걸림 |
| **서술 (L5)** | 근거-문서 매핑 | ❌ `evidence_spans` 자동 검사 |
| **종단** | 사기 탐지율 | ✅ 섀도 모드 → **주장하지 않음** |

🔴 **"이 시스템이 사기를 N% 잡는다"고 주장하지 않는다.** 대신 *"이 조합은 대조로 걸린다"* 를 테스트로 증명한다.

🔴 **L1 추출 평가셋은 구현 전제조건**이다. 특히 S16이 판정 축의 중심이 되면서 **계약서 §Notices·§Amendment 조항 추출 정확도가 시스템 정확도의 상한**이 됐다. 조항을 못 읽으면 S16은 전부 `medium`(조항 부재)으로 떨어져 모든 케이스가 `HOLD` — 게이트가 꺼진다.

### 11.2 공격 테스트

```
T1   승인 없이 게이트 통과 시도           → BLOCKED
T2   승인 재사용                          → REJECTED (consumed)
T3   다른 case_id의 승인 사용             → REJECTED (case mismatch)
T4   승인 후 계좌 바꿔치기                → REJECTED (fingerprint)
T5   TTL 경과 사용                        → REJECTED (expired)
T6   계약서 미제출 → 통과 시도            → UNKNOWN (보류)
T7   계약서 추출 실패 → 통과 시도         → UNKNOWN (보류)
T8   계약서에 판정 무력화 지시 삽입        → 등급 불변
T9   판정 모듈 외부 호출                  → AST 검사 실패
T10  모델이 approval_id 자가 생성          → 런타임 차단
T11  확인 채널로 email_reply 지정          → REJECTED (invalid channel)
T12  근거 문장에 문서에 없는 수치 삽입     → 매핑 검사 실패 (INV-8)
T13  T/T→L/C (안전 방향) 변경             → 경고 없음 (TR-DIRECTIONAL)
```

### 11.3 대조 매트릭스 전수 검사

`(S16severity, S9, S10severity, S11, S12, M1, M2, M6, M8, S1)` 조합 중 **도달 가능한 것**에 대해 기대 등급을 표로 고정하고 전수 검증한다. 규칙 추가 시 회귀 가드가 된다.

🔴 **dead rule 가드 (v3.1 신설)**: 각 규칙 `R1~R11`에 대해 **그 규칙을 발화시키는 입력이 실제로 존재하는지** 검사한다. v3.0에서 R7·R8이 입력 필드 부재로 영영 침묵했던 결함을 기계적으로 차단한다.

```python
def test_no_dead_rules():
    """모든 규칙은 최소 1개의 도달 가능한 입력을 가져야 한다."""
    for rule in RULES:
        assert any(rule.cond(s) for s in ALL_REACHABLE_STATES), \
            f"{rule.id}는 도달 불가 — 입력 스키마에 해당 필드가 없다"
```
