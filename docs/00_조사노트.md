### E-5. 🔴 문서 내 논리 오류 발견 (자체 감사)

v2 제안서 §1.1 시나리오가 **모순**이다:

> *"부산의 자동차부품 **수출업체**가… 12만 유로를 **보냅니다**"*

**수출업체는 대금을 받는 쪽이다.** 송금하는 쪽은 **수입업체 또는 해외 공급처에 대금을 지급하는 기업**이다. 본 시스템은 **송금인(payer) 측 게이트**이므로 시나리오 주체를 정정해야 한다.

BEC는 양방향으로 작동한다:
- **한국 수입업체가 해외 공급처에 지급** → 공급처 계좌가 바뀜 → **한국 기업이 손실** ← **본 시스템 대상**
- 한국 수출업체가 대금 수령 → 가짜 메일로 "우리 계좌 바뀜" → 바이어가 사기범에게 송금 → 손실은 바이어 측 ← 본 시스템 대상 아님

🔴 **차별점이 단 하나로 축소된다: 사람이 매뉴얼로 하는가 vs 시스템이 자동으로 하는가.**

### E-7. 은행별 수취계좌 확인 서비스 도입 현황

**공통 한계 (우리 기회)**: 두 은행 모두 **① 이름 대조** ② **영업점 방문** ③ **사용자가 능동 요청**. 온라인 송금 화면에서 자동 발동하지 않는다.

### E-8. 🔴 설계 결함 발견 — S1(NEW_ACCOUNT)은 판정자가 아니다

사용자 지적: *"이번에 계좌를 옮겼다고 하는데 그러면 계좌 과거이력이 없는 거잖아"*

**정확한 지적이다.** 정당한 계좌 변경도 이력이 없다. 따라서 **S1만으로는 사기와 정당한 변경을 구분할 수 없다.**

v2 명세서는 S1을 S2~S6, M1~M7과 **같은 층위의 신호 목록에 넣었다.** 이것이 오류다.

**정정된 역할 구분**:

| 층위 | 신호 | 역할 |
|---|---|---|
| **트리거 (게이트 개방)** | **S1** NEW_ACCOUNT | 사기 여부를 말하지 않는다. *"이때만 확인하게 만든다"* = 마찰 배치 결정 |
| **판별 (사기 vs 정당)** | S2 국가변경 · S3 국가불일치 · M1 도메인유사 · M2 회신단절 · M6 압박 | 실제로 둘을 가른다 |

R5(신규계좌 + 보강신호 없음 → HOLD)는 *"사기다"* 가 아니라 *"확인하고 가라"* 다. 명세서에 이 구분을 명시해야 한다.

### E-9. 사용자 지적에서 도출된 신규 신호 2개

*"새 계좌는 이력이 없다"* 를 뒤집으면 **계좌 자체의 속성**이 신호가 된다.

| ID | 신호 | 근거 | 데이터 확보 |
|---|---|---|---|
| **S7** | `ACCOUNT_AGE` — 수취계좌 개설 경과일 | 사기 계좌는 대개 **최근 개설**. 정당한 은행 변경은 기업 계좌라 이력이 있을 수 있음. **apexanalytix가 실제로 이 신호를 사용** (*"최근 개설된 계좌가 관련된 변경 요청을 알림"*) | 🔴 IBAN에 없음. 은행 간 조회 필요 `[미확인]` |
| **S8** | `FORMAL_NOTICE_ABSENT` — 공식 통지 부재 | 정당한 계좌 변경은 보통 **계약 수정·공문·인보이스 계좌 병기**로 사전 통지된다. 사기는 **이메일 한 통**이다 | 사용자 제출 문서로 확인 가능 |

**S8이 특히 값지다** — 데이터 확보가 쉽고(사용자가 계약서·기존 인보이스를 갖고 있다), *"정당한 변경 vs 사기"* 를 직접 가르며, 기존 제품 중 이 신호를 쓰는 곳이 확인되지 않았다.

### E-10. 증빙서류 법정 요건 — A안(S8) 데이터 기반

| 사실 | 출처 | 검증 |
|---|---|---|
| 연간 **10만 달러 초과** 송금 시 **계약서 등 지급 사유 입증 서류 제출 의무** | [3o3](https://app-q.3o3.co.kr/) · 한국은행 · [신한은행 안내](https://refininfo.com/shinhan-foreign-remittance-documents/) | [검증됨] |
| 은행은 **연 5만 달러 이상 송금에 증빙서류 확인 의무** | [세무사신문](https://webzine.kacta.or.kr/news/articleView.html?idxno=13504) | [검증됨] |
| **관계증빙서류 5년 보관 의무** | [관세청](https://www.customs.go.kr/kcs/cm/cntnts/cntntsView.do?mi=10368&cntntsId=5121) · 외국환거래규정(기재부고시 2019-12호) | [검증됨 — 단 주체 불명] |
| 🔴 **5년 보관 의무의 주체가 은행인가 기업인가** | — | **[미확인]** |

**주체 판정의 함의** (양쪽 다 A안이 성립하지만 설계가 달라진다):

| 주체 | A안 설계 | 장점 | 단점 |
|---|---|---|---|
| **기업** (현 근거상 유력) | 기업이 계약서·과거 인보이스를 **업로드** | **은행 내부 API 의존 0** — U-11 문제 소멸 | 업로드 마찰 |
| **은행** | 은행 DB에서 과거 인보이스 자동 대조 | 마찰 0 | 내부 연동 필요 |

🎯 **핵심 발견**: 어느 쪽이든 **기업은 법적으로 5년치 서류를 갖고 있다.** 따라서 A안은 v2의 U-11(KB 내부 송금 이력 API)에 **의존하지 않는다.** 이것이 A안이 v2보다 나은 결정적 이유다.

**추가 발견 — 마찰이 0일 수 있는 경로**: 기업은 **어차피 송금 신청 시 증빙서류를 은행에 제출한다**(법정 의무). 그 서류를 심사 과정에서 대조하면 추가 요구가 없다.

🔴 **단 이 경로는 조건부다** — 이번 제출분에 과거 인보이스는 없다:

| 필요 대조 | 이번 제출분에 있나 |
|---|---|
| 계약서의 결제조건·계좌 | ✅ 있음 (10만 달러 초과 시 제출 의무) |
| 이번 인보이스의 계좌 | ✅ 있음 |
| **과거 인보이스의 계좌** | ❌ **없음** — 기업 추가 제출 또는 은행 DB 필요 |

**→ 따라서 V3(무역 계약서에 계좌번호 기재율)가 이제 V2보다 중요하다.**
- 계약서에 계좌가 있으면 → **계약서 vs 이번 인보이스** 대조로 충분. 과거 인보이스 불필요
- 계약서에 계좌가 없으면 → 과거 인보이스 필요 (마찰 발생)

### E-11. ✅ V3 확인 — 무역 계약서에 **계좌번호는 없다**. 대신 더 좋은 것이 있다

한국무역협회 표준 무역계약서 결제조건(Terms of Payment) 항목 실측:

> *"선급(advance payment) · 일람불(at sight) · 연불 · 분할지급 / CAD · COD / **L/C에 의한 지급**(At sight L/C, Usance L/C) / **D/P · D/A** / 화환어음 약정: 어음 기간, 선적서류 인도조건, 어음 결제지"*
> — [한국무역협회 무역서식](https://www.kita.net/cmmrcinfo/cmmrcFormat/oldCmmrcformat/oldCmmrcformatDetail.do)

**결제 방법·시기·통화·장소만 기재. 계좌번호 없음.** [ICC Model International Sale Contract](https://m.blog.naver.com/PostView.naver?blogId=ankey&logNo=34382226) §5도 동일 (선지급액·화환신용장 개설만).

**→ "계약서 계좌 vs 이번 계좌" 대조는 불가능하다.** 계좌는 인보이스에만 있다.

### E-12. 🎯 계약서에서 실제로 나오는 신호 3개 — 이번 제출분만으로 가능

계좌가 없어도 계약서에는 **대조 가능한 것이 남는다**. 그리고 **과거 인보이스가 필요 없다** — 이번 송금 신청 시 제출되는 서류만으로 판정된다.

| ID | 신호 | 대조 방식 | 필요 서류 | 신규성 |
|---|---|---|---|---|
| **S9** | `CONTRACT_COUNTRY_MISMATCH` — 계약 당사자 소재국 ≠ 수취계좌 개설국 | 계약서 당사자 주소 vs IBAN 국가코드 | 계약서 + 송금신청 | 🎯 **금감원 지시 항목과 정확히 일치** |
| **S10** | `PAYMENT_TERMS_MISMATCH` — 계약서 결제조건 ≠ 실제 송금 방식 | 계약서 §Terms of Payment vs 송금 종류 | 계약서 + 송금신청 | ⚪ **기존 제품 사용 확인 0건** |
| **S11** | `BENEFICIARY_NAME_MISMATCH` — 계약서 수익자명 ≠ 수취인명 | 계약서 당사자명 vs 수취인명 | 계약서 + 송금신청 | 🔴 VoP와 중복 |

**S9의 가치**: 독일 회사와 체결한 계약서인데 리투아니아 계좌로 송금 → **계약서 한 장으로 걸린다.** 그리고 금감원이 전 은행에 지시한 항목(*"수취인 국가와 수취 은행 소재 국가가 서로 다르거나"*)이 바로 이것이다. **은행이 이미 계약서를 받고 있는데 이 대조를 하지 않는다.**

**S10이 이 프로젝트에서 나온 가장 신규성 있는 신호일 수 있다**:
계약서가 **L/C(신용장)** 인데 갑자기 **T/T(전신송금)** 로 보내라고 하면 사기의 전형이다 — L/C는 은행이 지급을 보증하므로 사기범이 가져갈 수 없고, **T/T는 계좌로 직접 들어간다**. 즉 사기범은 결제 방식을 L/C에서 T/T로 바꾸도록 유도할 강한 동기가 있다.
🔴 이 신호를 사용하는 기존 제품을 **확인하지 못했다** — ERP 벤더는 계약서를 보지 않고 벤더 마스터만 본다.

### E-13. A안 설계 재정의 — 병목이 사라졌다

| | 초기 A안 (S8 중심) | **수정 A안 (S9·S10 중심)** |
|---|---|---|
| 핵심 신호 | 공식 통지 부재 | **계약서 ↔ 송금 정보 대조** |
| 필요 서류 | 계약서 + **과거 인보이스** | **계약서 + 이번 송금신청만** |
| 과거 이력 의존 | 있음 | **없음** |
| 추가 사용자 마찰 | 과거 인보이스 업로드 | **0 — 법정 제출 서류 그대로** |
| 규제 정합성 | 간접 | 🎯 **금감원 지시 항목 직접 이행 (S9)** |
| 평가셋 | 불필요 (대조) | **불필요 (대조)** |

**→ V2(서류 보관 주체)도 V3(계약서 계좌 기재)도 더 이상 병목이 아니다.** 이번 송금 신청 시 법정 제출되는 계약서 한 장으로 S9·S10이 나온다.

**남은 미확인**: V4 (계약서 notice clause 존재율 — S8 부가 신호용, 필수 아님)

### E-14. ✅ R-3 해소 — 국내 은행 AI 외화송금 시스템은 **정반대 방향**이다

**결정적 근거** — 신한은행 「AI 기반 이상 외화송금 탐지 프로세스」(2024-07 시행)가 무엇을 탐지하는지:

> *"**이상 외화송금이란 무역 거래를 가장한 해외송금, 소자본 신설업체의 단기간 내 거액 송금 등 비정상적인 외화송금 거래**"*
> — [ZDNet Korea, 2024-07-12](https://zdnet.co.kr/view/?no=20240712150129)

🎯 **방향이 반대다**:

| | 신한 시스템 | **KB Payee Guard** |
|---|---|---|
| 질문 | *"무역 거래를 **가장한** 송금인가"* | *"진짜 무역인데 **수취계좌가 바뀌었나**"* |
| 고객을 보는 시각 | **사기꾼일 수 있다** | **피해자일 수 있다** |
| 보호 대상 | **은행** (규제·AML 리스크) | **고객** (대금 손실) |
| 판정 근거 | 거래 패턴·업체 규모 | **계약서 문서 대조** |

**BEC 피해자는 정상 무역업체가 정상 거래를 하려는 것**이므로 "무역 거래를 가장한 송금" 필터에 걸리지 않는다. 실제로 무역 거래이기 때문이다.

### E-16. 🔴🔴 자체 검증에서 v3.0 설계 결함 3건 발견 (2026-07-30)

> **출처**: 본 세션의 독립 심사 에이전트(judge-v3) + 자체 grep 확인. **웹 조사가 아니라 자기 문서 감사에서 나왔다.**

#### 결함 1 — 최빈 BEC에서 모든 신호가 침묵한다 `[검증됨 — 규칙 테이블 수기 추적]`

v3.0의 판별 신호는 S9(소재국)·S10(결제조건)·S11(수취인명) 셋이다. 그런데 **가장 흔한 BEC 시나리오**를 대입하면:

| 신호 | 최빈 케이스 (같은 독일, 같은 BAUER GmbH, 같은 T/T, 계좌번호만 교체) |
|---|---|
| S9 | ❌ 불발 — DE = DE |
| S10 | ❌ 불발 — T/T = T/T |
| S11 | ❌ 불발 — 이름 일치 |
| **결과** | 🔴 **PASS로 통과** |

사기범은 **굳이 다른 나라 계좌를 쓸 이유도, 결제방식을 바꿀 이유도 없다.** 같은 나라 같은 이름으로 계좌를 열면 v3.0은 전부 통과시킨다.

#### 결함 2 — dead rule `[검증됨 — grep 실측]`

```
RemittanceRequest: case_id · payee_name · new_account · amount ·
                   remittance_type · contract · invoice · change_request
                   → 이력 필드 없음 ✅ 확인
AssessState에 "history" 문자열: 0건 ✅ 확인
R7·R8은 s.S1을 참조 → 입력원 없음 → 절대 발화 안 함 ✅ 확인
```

**규칙이 문서에 적혀 있는 것과 그 규칙이 발화하는 것은 다르다.** 데모 D8(*"이름 일치, 계좌만 다름"*)이 **도달 불가**였다.

#### 결함 3 — *"평가셋 불필요"* 는 과장 `[검증됨 — 논리]`

판정이 결정론이어도 **입력이 틀리면 결정론적으로 틀린 답**이 나온다. judge-v3 표현: *"Garbage in, deterministic garbage out."*

#### 🎯 해소 — S16 ACCOUNT_INSTRUCTION_PROVENANCE

**질문**: *"이 계좌 지시가 계약이 정한 경로로 왔는가?"*

근거: **계약서 §Notices·§Amendment는 체결 시점에 확정되므로, 은행 보관 원본을 기준으로 삼는 한 사기범이 사후에 바꿀 수 없다** (새 수정합의서 위조는 별개 — 전건 미탐). 계좌번호는 바꿔도, 3년 전 계약서의 *"변경은 양측 서면 합의로"* 는 못 바꾼다.

🔴 **2026-08-03 정정 — 근거 없는 단정이었다.**

이전 문장: *"은행은 송금 신청 시 «이 계좌 정보를 어디서 받으셨습니까»를 이미 묻는다 — 새 입력이 아니라 이미 받는 정보다 (사용자 능동성 0)."*

**E-1~E-16 어디에도 이를 뒷받침하는 근거가 없다.** 은행 송금 신청서 서식 실물을 확인한 적이 없다.
그런데 이 문장은 **S16의 오른쪽 입력 전체**를 떠받치고 있었다 —
S16 = `[계약이 허용한 경로] ∩ [이번 지시가 온 경로]` 에서 오른쪽이 없으면 신호 자체가 성립하지 않는다.

**정정된 서술**: 오른쪽 입력은 송금 신청 폼의 **항목 1개**로 받는다. 은행이 이미 묻는지는 **미확인**이며,
묻지 않는다면 **드롭다운 1개 추가**가 필요하다(새 서류가 아니라 기존 폼의 필드).
따라서 *"사용자 부담 0"* 이 아니라 *"부담 최소"* 가 정확하다.

**남은 확인 과제 (U-19 신설)**: 국내 은행 해외송금 신청서 서식에 계좌 정보 취득 경위 항목이 있는가.
Codex cross-model 리뷰(2026-08-02)도 같은 지점을 지적했다 —
*"모든 대상 은행과 채널에서 구조화된 값으로 수집하는지 증거가 없습니다. 자유기재나 미수집이면 S16 입력 자체가 성립하지 않습니다."*

#### 🔴 왜 이 결함들이 생겼는가 (근본 원인)

v3는 *"과거 이력에 의존하지 말자"* 는 **옳은 방향**으로 갔다. 그런데 이력을 **판별자에서 내리면서 트리거로서의 역할까지 같이 버렸다.** 이력이 필요 없어진 게 아니라 **입력 스키마에서 사라졌고**, 그것을 참조하던 규칙이 조용히 죽었다.

**결정적으로 [E-6](#e-6)을 잘못 읽었다.** 6개 은행이 *"같은 계좌가 표시된 외화송금확인서"* 를 발급한다는 사실을 *"은행이 이미 하고 있다 = 차별성 손실"* 로만 읽었는데, 같은 문장이 **"은행은 이미 수취인 계좌 이력을 보유한다"(U-11 긍정 해소)** 를 증명한다.

> judge-v3: *"막히지도 않은 병목을 우회하려고 최빈 케이스 탐지력을 버렸다."*

## C. 이 프로젝트에 불리한 발견 (정직 기재)

1. **메일에서 BEC를 읽는 기능은 이미 상용화됨** (A-1). 그 축으로는 이길 수 없다.
2. **cheKB(4회 입상)와 "문서를 읽어 위험을 지목한다"는 형태가 유사**하다. 심사위원이 형태로 기억하면 재탕 지적을 받는다.
3. **U-2가 최악으로 나오면**(EU VoP가 국제 송금까지 커버) 차별성이 크게 깎인다.
4. **U-18이 존재하면** 프로젝트 재설계가 필요하다.
5. **U-11이 부정이면** Tier B가 무너지고 KB 의존도가 도로 올라간다.

> 이 5개를 제안서에서 숨기지 않는다. 심사장에서 먼저 지적당하는 것보다 먼저 말하는 편이 낫다.
